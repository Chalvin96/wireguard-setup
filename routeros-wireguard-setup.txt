Mikrotik / RouterOS — site-specific manual configuration
=========================================================

The WireGuard tunnel itself (interface, peer, address, route, and the CGNAT
self-healing watchdog) is provisioned automatically by the Ansible role:

    ansible/roles/mikrotik-wireguard/

It runs via `ansible/site.yml` (hosts group `mikrotik`) and is idempotent —
safe to re-run. It needs:

  1. SSH access: import your pubkey once on the router
       /user/ssh-keys/import user=admin public-key-file=<your-key>.pub
     (upload the file first, e.g. via Winbox file list or scp)
  2. `vault_wireguard_client_private_key` and
     `vault_wireguard_client_public_key` in ansible/group_vars/all/vault.yml
     (the verify task asserts the interface key matches the public key)
  3. The `mikrotik_*` variables from ansible/group_vars/all/config.yml.example
     copied into your config.yml

Design note: the role leaves the interface listen-port unchanged on existing
routers and uses the RouterOS default when creating an interface. The
`wg-watchdog` scheduler (default: every 2m) pings the VPS tunnel IP; when all
three probes fail it disables the interface for 60s, requests a random port
(`listen-port=0`), and re-enables. This may help recover stale NAT mappings,
but neither a different external port nor recovery is guaranteed. ICMP
filtering can trigger unnecessary resets. Ordinary reconnects do not rotate
the port. A `site.yml` run enforces enabled state: a manually disabled
`wg-to-vps` interface or `wg-watchdog` scheduler is re-enabled on the next
run. The role reports changed on every apply; it does not compute a diff.

The rules below are intentionally NOT managed by Ansible — firewall and NAT
policy are site-specific. Reference for a new site (assumes the edge peer is
10.8.0.2, personal clients start at 10.8.0.3):

# Let LAN devices reply to personal WireGuard clients without adding routes on
# every LAN host. Replace 192.168.1.0/24 with your LAN CIDR.
/ip/firewall/nat
add chain=srcnat \
    src-address=10.8.0.0/24 dst-address=192.168.1.0/24 \
    action=masquerade comment="NAT WireGuard clients to LAN"

# Allow personal WireGuard clients to reach the LAN.
/ip/firewall/filter
add chain=forward \
    src-address=10.8.0.3-10.8.0.254 dst-address=192.168.1.0/24 \
    action=accept comment="Allow personal WireGuard clients to LAN"

# Optional hardening: the VPS itself may only reach the edge HTTP/HTTPS service.
# Replace LOCAL_SERVER_IP with the edge node LAN IP that Caddy listens on.
/ip/firewall/filter
add chain=forward \
    src-address=10.8.0.1 dst-address=LOCAL_SERVER_IP \
    protocol=tcp dst-port=80,443 \
    action=accept comment="Allow VPS to edge HTTP and HTTPS"

/ip/firewall/filter
add chain=forward \
    src-address=10.8.0.1 dst-address=192.168.1.0/24 \
    action=drop comment="Block VPS from the rest of LAN"

# Forward HTTP/HTTPS to local server
/ip/firewall/nat
add chain=dstnat in-interface=wg-to-vps \
    protocol=tcp dst-port=80 \
    action=dst-nat to-addresses=LOCAL_SERVER_IP to-ports=80

/ip/firewall/nat
add chain=dstnat in-interface=wg-to-vps \
    protocol=tcp dst-port=443 \
    action=dst-nat to-addresses=LOCAL_SERVER_IP to-ports=443
